# LatencyTest1 - first latency test (2 devices, no laptop)

> Back to [Latency and network README](../README.md)

Self-contained scripts that measure **leader** and **sensing** latency on the two
edge boards as the number of exposed tools grows. They bypass `main.py` (no
Telegram, no election, no backup) but use the **live preset models, the live
prompts, and the live dispatch path** (`LeaderNetwork` + `tool_registry` +
`tool_dispatcher`), so the timed stages match what a real leader does. The two
LLM stages are generated by **streaming** the live model (same prompts the live
hooks build) so time-to-first-token and decode tk/s can be measured; the picked
tool is still dispatched over the real network to the sensing agent, which runs
the real skill. No new presets are added and no live module is modified.

Stdlib only in this folder; the heavy runtimes (Hailo, llama.cpp, TFLite, camera)
come in only through the live preset modules the scripts import.

## What is measured

Each device has two modes; each mode is tested once as leader and once as sensing.

| Couple | Leader (preset under test) | Sensing (preset under test) |
|---|---|---|
| A | Raspberry Pi 5 - qwen3 on Hailo (`Workflow1`) | STM32 - `stm32mp257_yolo_CPU` person detection |
| B | STM32 - functiongemma on CPU (`stm32mp257fdk_leader`) | Raspberry Pi 5 - `raspberrypi5_yolo_NPU` (object detection filtered to `person`) |

Both couples expose the **same tool name and description** (`detect_people`,
`"Detects the people that are currently visible. ..."`, defined once in
`bench_core`), so the two leaders are dispatched on an identical prompt and their
numbers are directly comparable. For **5 configurations** the sensing agent really
exposes **1, 6, 12, 18, 24** tools (`detect_people` + `wrong_tool_1..N-1`). Each
config runs the **same 10 person-detection queries**.

**Leader**, once at startup:
- `time_to_boot` - absolute LLM cold-start: the model is loaded **10 times**, fully
  evicted between loads (the model file is already on disk, so the download is not
  timed), and saved as `{samples, mean, std, min, max}` in **ms**.

**Leader**, per query (saved after every query, so a crash loses nothing):
- `query_to_tool_ms`   - query received to tool call ready (dispatch generation)
- `dispatch_ttft_ms`   - query received to **first** dispatch token (prefill included)
- `dispatch_tokens_in` / `dispatch_tokens_out` / `dispatch_tps` - dispatch prompt tokens, generated tokens, decode tk/s
- `tool_to_result_ms`  - tool sent to result received (`net.dispatch()`, real network round-trip, skill runs on the sensing board)
- `result_to_reply_ms` - result received to final reply ready (answer generation)
- `answer_ttft_ms` / `answer_tokens_in` / `answer_tokens_out` / `answer_tps` - the same for the answer stage

  `tokens_in` is exact on the STM32 (llama.cpp). On the Pi/Hailo the genai
  streaming API does not expose prompt tokens, so `*_tokens_in` is `null` there
  (`*_tokens_out` is still counted from the token stream).
- plus `{query, tool_called, tool_result, final_reply}`, `correct`, `end_to_end_ms`
- plus a per-config and overall aggregate (avg/std/min/max of each metric).

**Leader**, `prompt_specs` (one entry per tool count) records exactly what the LLM
was fed for that config:
- `tools` - the full tool defs attached (name + description + parameters).
- `dispatch_prompt` - the precise tool-call-stage prompt (system prompt + the N
  tool declarations + the user query). On the STM32 this is the exact
  FunctionGemma-rendered string; on the Pi/Hailo it is the `messages` + attached
  tool names passed to `generate()` (the genai template is applied internally, so
  the rendered string is not exposed).
- `answer_prompt` - the same for the tool-reply stage (system prompt + the called
  tool + the tool result). Both are captured live from the first query of the
  config that exercises each stage, so `dispatch_prompt` embeds that query's text.

**Sensing**, per `tools/call`:
- `time_to_reply_s` - tool received to result sent (no network lag), in **seconds**
- on finish: avg +- std of `time_to_reply` **per tool count and overall** (over
  the correct-tool calls; a warmup call and any mis-dispatched wrong-tool calls
  are excluded).

## How to run

Run from the `IMPLEMENTATION/` folder. **Start the sensing script first**, then the
leader script (the leader is the orchestrator: it sets the configs, sends the
queries, and signals the end). You type nothing during a run.

### Couple A - Raspberry leads, STM32 senses
```
# on the STM32
python LatencyTest1/test_stm32_sensing.py
# then on the Raspberry Pi
python LatencyTest1/test_raspberry_leader.py
```

### Couple B - STM32 leads, Raspberry senses
```
# on the Raspberry Pi
python LatencyTest1/test_raspberry_sensing.py
# then on the STM32
python LatencyTest1/test_stm32_leader.py
```

Do couple A completely and let both sides exit **before** starting couple B, so
the Hailo device is only used by one process at a time.

Each leader runs configs `1 -> 6 -> 12 -> 18 -> 24` automatically, then tells the
sensing agent it is done; both sides write their JSON and exit. If you need to
stop the sensing side early, Ctrl-C writes whatever it collected so far.

## Output

Written to `LatencyTest1/results/`:
- `leader_<device>_<timestamp>.json`  - `samples` (per query) + `aggregate` (per config).
- `sensing_<device>_<timestamp>.json` - `calls` (per tools/call) + `per_config` + `overall`.

## Coordination (test-only control messages)

The leader and sensing scripts speak two extra operational-plane messages, used
**only** by these scripts:

| Message | Direction | Shape |
|---|---|---|
| `bench/set_tools` | Leader -> Sensing | `{"jsonrpc":"2.0","id":..,"method":"bench/set_tools","params":{"n":<int>,"correct_tool":"detect_people"}}` |
| `bench/done`      | Leader -> Sensing | `{"jsonrpc":"2.0","id":..,"method":"bench/done"}` |

On `bench/set_tools` the sensing agent rebuilds its exposed `tool_defs` to `n`
entries; the leader then re-pulls `tools/list` until its registry shows `n` tools
before sending the queries. These are intentionally **not** part of the
production protocol (`sensing_agent.py` / the protocol docs are unchanged) - they
exist only for this benchmark, which never runs inside `main.py`.

## Notes on fidelity

The leader stages build the **same prompts** the live workflow hooks build
(`stm32mp257fdk_leader._dispatch`/`_answer` for couple B, `Workflow1` for couple
A), on the same model objects, with the same real TCP hop to the sensing agent.
The only reason the bench streams the generation itself instead of calling the
hooks verbatim is that the hooks return the finished text, which cannot expose
time-to-first-token; streaming yields identical output while clocking the first
token and the decode rate. What `main.py` adds around those stages (Telegram
send/typing, conversation backup, election) sits **outside** the measured
intervals. The FunctionGemma (couple B) path calls `llm.reset()` before each
generation so every query is an independent cold prefill (no KV-cache carry-over
between queries); the Hailo (couple A) path calls `clear_context()`, as the live
Workflow1 does. The per-config `bench/set_tools` + re-pull handshake runs once per
config, never inside a timed query. The sensing side does one warmup detection at
startup so model/camera load does not land in the first measured call.
